# استاندارد رابط کاربری سیستم مدیریت تحویل و حساب

وضعیت سند: تثبیت‌شده برای اجرای مرحله دوم  
دامنه: `frontend/src`  
زبان و جهت: فارسی و راست‌به‌چپ

## 1. هدف محصول و اصل طراحی

این نرم‌افزار یک ابزار داخلی برای مدیر و ادمین مجموعه است. جریان اصلی آن از «لیست تحویل» شروع می‌شود و با ثبت برگشت، صدور و ارسال فاکتور و ثبت تسویه ادامه پیدا می‌کند.

اصل رابط کاربری:

- هر لیست، پرونده اصلی عملیات است.
- فاکتور و پرداخت در دیتابیس موجودیت‌های مستقل باقی می‌مانند، اما در رابط کاربری داخل همان پرونده مدیریت می‌شوند.
- جدول، ابزار اصلی مشاهده و مدیریت داده است.
- همه صفحات باید از یک زبان بصری، یک ساختار صفحه و کامپوننت‌های مشترک استفاده کنند.
- وضعیت‌ها از نتیجه عملیات محاسبه می‌شوند؛ کاربر عملیات را ثبت می‌کند، نه اینکه نتیجه ناسازگار را آزادانه انتخاب کند.

## 2. نتیجه ممیزی وضع موجود

ممیزی روی 43 فایل Vue انجام شد.

| مورد | تعداد | استفاده از استاندارد مشترک موجود |
|---|---:|---:|
| جدول | 23 | صفر جدول از `app-table` استفاده می‌کند |
| دکمه | 135 | فقط 59 دکمه از خانواده `app-button` استفاده می‌کند |
| لایه یا مودال | 15 | صفر مودال از `app-modal` استفاده می‌کند |

مشکلات اصلی:

1. جدول‌ها headerهای آبی، خاکستری و سفید متفاوت دارند.
2. ضخامت و رنگ border بین `gray-100`، `gray-200`، `slate-100` و `slate-300` تغییر می‌کند.
3. ارتفاع ورودی‌ها بین 40، 44 و 48 پیکسل متغیر است.
4. دکمه عملیات در بعضی صفحات گرد و آیکنی و در بعضی صفحات مستطیلی و متنی است.
5. رنگ اصلی بین `blue` و `indigo` جابه‌جا می‌شود.
6. مودال‌ها header، footer، عرض، backdrop و `z-index` یکسان ندارند.
7. متن و رنگ یک وضعیت در چند فایل جدا تعریف شده و مستعد اختلاف است.
8. فیلترها گاهی داخل نوار عملیات کناری و گاهی بالای جدول هستند.
9. صفحه حساب قدیمی، فاکتور مستقل از لیست ایجاد می‌کند و با جریان جدید محصول هم‌پوشانی دارد.
10. کلاس‌های مشترک اولیه در `style.css` تعریف شده‌اند، اما بیشتر صفحات آن‌ها را دور زده‌اند.

## 3. معماری نهایی صفحات

منوی اصلی به این ترتیب خواهد بود:

1. خانه
2. مدیریت لیست‌ها
3. مشتریان
4. محصولات
5. گزارش‌ها
6. ادمین‌ها ـ فقط مدیر
7. تنظیمات ـ فقط مدیر

قواعد:

- «حساب» به‌عنوان صفحه عملیاتی مستقل حذف می‌شود.
- «حساب جدید» حذف می‌شود؛ عملیات مالی جدید فقط از یک لیست ایجاد می‌شود.
- پیش‌نویس‌ها یک فیلتر یا تب در صفحه مدیریت لیست‌ها هستند.
- حساب‌ها و فاکتورهای قدیمی تا زمان تعیین تکلیف مهاجرت در نمای «آرشیو قدیمی» فقط برای مشاهده و ویرایش محدود باقی می‌مانند.
- گزارش‌ها صفحه مستقل خود را حفظ می‌کنند، اما از همان اجزای بصری استفاده می‌کنند.

## 4. ساختار ثابت هر صفحه

هر route اصلی باید به این ترتیب ساخته شود:

1. `AppPageHeader`: عنوان، توضیح کوتاه، وضعیت یا شمارنده و اقدام اصلی.
2. `AppFilterBar`: جستجو، فیلترها، مرتب‌سازی و پاک‌کردن فیلتر.
3. خلاصه آماری اختیاری با `AppStatCard`.
4. `AppTablePanel`: عنوان جدول اختیاری، جدول، حالت loading/empty/error و pagination.
5. مودال‌های عملیات.

نوار عملیات کناری فقط برای اقدام‌هاست، نه فیلترها:

- حداکثر سه اقدام پرتکرار.
- اقدام اصلی در بالا.
- اقدام ثانویه بعد از آن.
- اقدام خطرناک فقط در محل مرتبط و پس از تأیید.
- جستجو، وضعیت و تاریخ همیشه داخل `AppFilterBar` بالای جدول قرار می‌گیرند.

## 5. شبکه فاصله‌گذاری و اندازه‌ها

واحدهای مجاز فاصله:

| کاربرد | مقدار |
|---|---:|
| فاصله بسیار کوچک | 4px |
| فاصله اجزای مرتبط | 8px |
| فاصله کنترل‌ها | 12px |
| padding استاندارد | 16px |
| فاصله بخش‌ها | 24px |
| فاصله بزرگ | 32px |

قواعد اندازه:

- شعاع استاندارد تمام کنترل‌ها، پنل‌ها و badgeها: `8px` (`rounded-lg`).
- سایه پنل‌ها: فقط `shadow-sm`.
- ارتفاع کنترل فیلتر: `44px`.
- ارتفاع کنترل فرم: `48px`.
- ارتفاع دکمه عادی: `40px`.
- ارتفاع دکمه اصلی فرم: `48px`.
- حداقل ارتفاع سطر جدول: `52px`.
- محتوای صفحه: تمام عرض موجود با padding برابر `16px` در موبایل و `24px` در دسکتاپ.

استفاده از `rounded-full` فقط برای spinner، avatar و نقاط اعلان مجاز است؛ badge وضعیت و دکمه عملیات گرد کامل نمی‌شوند.

## 7. استاندارد جدول

کاربر تفکیک واضح سطر و ستون را ترجیح می‌دهد. تمام جدول‌های عملیاتی باید این قرارداد را رعایت کنند:

- `border-collapse` فعال.
- border بیرونی و تمام سلول‌ها `1px solid slate-300`.
- header با پس‌زمینه `slate-100`.
- متن header اندازه 12px، وزن 700 و بدون letter spacing لاتین.
- متن سلول اندازه 14px.
- padding header برابر `12px 16px`.
- padding سلول برابر `12px 16px`.
- hover سطر برابر `slate-50`.
- سطر انتخاب‌شده برابر `indigo-50` با نشانه کناری indigo.
- مبلغ‌ها و تعدادها راست‌چین؛ ورودی‌های لاتین مانند تلفن و شناسه با `dir=ltr` اما در ستون ثابت.
- جدول در عرض کم به کارت تبدیل نمی‌شود و horizontal scroll خواهد داشت.
- header جدول‌های طولانی sticky می‌شود.
- ستون عملیات در سمت چپ جدول sticky می‌شود، اگر عرض جدول از viewport بیشتر باشد.
- empty، loading و error داخل همان قاب جدول نمایش داده می‌شوند.
- pagination همیشه پایین جدول و با border بالایی قرار می‌گیرد.

### جدول اصلی مدیریت لیست‌ها

هر سطر نماینده یک لیست است:

| ستون | رفتار |
|---|---|
| شماره لیست | لینک ورود به جزئیات؛ برای پیش‌نویس متن «پیش‌نویس» |
| مشتری | نام مشتری؛ کلیک برای مشاهده پرونده مشتری |
| تاریخ تحویل | تاریخ و ساعت ثبت‌شده |
| تاریخ برگشت | آخرین برگشت واقعی؛ تا پیش از برگشت خالی |
| وضعیت لیست | دکمه وضعیت؛ بازکردن مدیریت برگشت |
| فاکتور | وضعیت، تعداد فاکتورها و شماره آخرین فاکتور |
| مبلغ | مجموع فاکتورهای معتبر |
| وضعیت ارسال | وضعیت تجمیعی فاکتورها؛ قابل کلیک |
| وضعیت تسویه | وضعیت محاسبه‌شده؛ قابل کلیک |
| عملیات | یک اقدام اصلی و منوی عملیات بیشتر |

ستون‌های اقلام، تعداد ردیف و آخرین ذخیره در این جدول نمایش داده نمی‌شوند و فقط در جزئیات لیست قرار می‌گیرند.

### جدول مالی داخل جزئیات لیست

هر سطر نماینده یک فاکتور است:

| شماره فاکتور | نوع | پیوست به | مبلغ فاکتور | پرداخت‌شده | مانده | ارسال | تسویه | عملیات |
|---|---|---|---:|---:|---:|---|---|---|

پرداخت‌ها با بازشدن همان سطر یا در modal تسویه نمایش داده می‌شوند. رکورد پرداخت و رکورد فاکتور در دیتابیس یکی نمی‌شوند.

## 8. دکمه‌ها و عملیات

تمام دکمه‌ها از یک کامپوننت یا کلاس مرکزی استفاده می‌کنند.

| variant | کاربرد | رنگ |
|---|---|---|
| primary | ایجاد، ادامه جریان، ذخیره اصلی | Indigo solid |
| secondary | بازگشت، بستن، اقدام خنثی | White/Slate border |
| success | ثبت تحویل، ثبت برگشت سالم، تأیید موفق | Emerald solid |
| warning | پیگیری، تغییر حساس غیرمخرب | Amber soft |
| danger | حذف، ابطال، غیرفعال‌سازی | Rose soft یا solid |
| ghost | اقدام کم‌اهمیت داخل جدول | Transparent/Slate |

قواعد:

- دکمه متنی داخل جدول ارتفاع 32px دارد.
- آیکن بدون متن فقط برای عملیات کاملاً شناخته‌شده مثل ویرایش و حذف مجاز است و باید tooltip داشته باشد.
- در هر ناحیه فقط یک دکمه primary وجود دارد.
- حذف و ابطال همیشه confirmation می‌گیرند.
- تغییر وضعیت ارسال‌شده به ارسال‌نشده، ابطال پرداخت، غیرفعال‌سازی ادمین و حذف محصول confirmation می‌گیرند.
- actionهای غیرفعال باید علت خود را در tooltip یا متن کمکی نشان دهند.

## 10. فرم‌ها

- label بالای فیلد، اندازه 14px و وزن 600.
- فیلد الزامی با متن «الزامی» یا ستاره و پیام واضح مشخص می‌شود.
- input، textarea، select، date picker و lookup ارتفاع و focus یکسان دارند.
- focus برابر border indigo و ring کم‌رنگ indigo است.
- پیام خطا زیر همان فیلد با rose نمایش داده می‌شود.
- متن راهنما زیر فیلد با slate-500 نمایش داده می‌شود.
- فرم‌های بیش از شش فیلد به بخش‌های نام‌دار تقسیم می‌شوند.
- دکمه‌های footer فرم ترتیب ثابت دارند: اقدام اصلی، سپس انصراف.

## 11. مودال‌ها

تمام modalهای واقعی از `AppModal` استفاده می‌کنند. dropdown، date picker و lookup modal محسوب نمی‌شوند.

ساختار ثابت:

1. backdrop با `slate-950/50`.
2. `z-index` پایه 160؛ confirmation روی modal با 170.
3. header سفید با border پایین، عنوان، توضیح اختیاری و دکمه بستن.
4. body اسکرول‌پذیر با padding 24px.
5. footer sticky سفید با border بالا و دکمه‌های استاندارد.

اندازه‌ها:

| size | حداکثر عرض | کاربرد |
|---|---:|---|
| sm | 400px | confirmation |
| md | 560px | فرم مشتری و ادمین |
| lg | 800px | محصول و فرم فاکتور ساده |
| xl | 1200px | برگشت، صدور فاکتور، ارسال و تسویه |
| full | `calc(100vw - 32px)` | پیش‌نمایش PDF |

تمام modalها با Escape بسته می‌شوند، focus داخل modal نگه داشته می‌شود و هنگام عملیات در حال ذخیره بسته نمی‌شوند.

## 13. رفتار واکنش‌گرا

- desktop اولویت اصلی سیستم است، زیرا نرم‌افزار داخلی و جدول‌محور است.
- در عرض کمتر از 1024px، action sidebar به action bar بالای محتوا تبدیل می‌شود.
- جدول‌ها horizontal scroll دارند و ترتیب ستون‌ها حفظ می‌شود.
- فیلترها در موبایل یک‌ستونه می‌شوند.
- footer مودال در موبایل دکمه‌های تمام‌عرض دارد.
- هیچ داده مهمی صرفاً با hover قابل دسترسی نیست.

## 14. قرارداد کامپوننت‌های مرحله دوم

| کامپوننت | مسئولیت |
|---|---|
| `AppPageHeader` | عنوان، توضیح، شمارنده و اقدام اصلی |
| `AppFilterBar` | search، select، date و clear |

## 15. ترتیب انتقال صفحات

1. جدول مدیریت لیست‌ها و ادغام نمای حساب.
2. جزئیات لیست و جدول مالی فاکتور/پرداخت.
3. modalهای برگشت، فاکتور، ارسال و تسویه.
4. مشتریان و جزئیات مشتری.
5. محصولات و دسته‌بندی.
6. ادمین‌ها و تنظیمات.
7. خانه و گزارش‌ها.
8. login، حالت‌های loading/empty/error و جزئیات واکنش‌گرا.

## 16. معیار پذیرش یکپارچگی

مرحله بازطراحی زمانی پذیرفته است که:

- همه جدول‌های عملیاتی از یک component/style مرکزی استفاده کنند.
- همه modalهای واقعی از `AppModal` استفاده کنند.
- هیچ رنگ وضعیت در routeها تکرار نشده باشد.
- هیچ دکمه عملیاتی style مستقل و خارج از variantهای تعریف‌شده نداشته باشد.
- جستجو و فیلتر همه صفحات ارتفاع، border و focus یکسان داشته باشند.
- جدول‌ها خطوط واضح سطر و ستون داشته باشند.
- صفحه مستقل ساخت حساب جدید وجود نداشته باشد.
- مدیر بتواند وضعیت لیست، فاکتور، ارسال و تسویه را از جدول مدیریت لیست‌ها مشاهده و آغاز کند.
- خروجی desktop و mobile با آزمون تصویری بررسی شود.
- build فرانت‌اند و تست‌های بک‌اند بدون خطا باشند.

## 17. تصمیم‌های خارج از دامنه مرحله اول

در این مرحله منطق تجاری، API و دیتابیس تغییر نمی‌کنند. موارد زیر در مرحله پیاده‌سازی تعیین تکلیف می‌شوند:
